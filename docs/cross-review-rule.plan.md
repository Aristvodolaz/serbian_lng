# План: универсальное правило кросс-ревью (ECC)

Дата: 2026-10-09
Статус: на согласовании — реализация не начата.

## Цель

Сделать универсальное (не привязанное к конкретной фиче) правило ревью на основе
примера «Кросс-ревью фичи: Passkey login flow», с поддержкой:

- **кросс-ревью** — два участника (Ревьюер A / Ревьюер B), раунды, спорные пункты,
  голосование;
- **обычного ревью** — один проход по чек-листу, для небольших диффов.

## Где будет жить правило (итоговый артефакт)

Кастомный скилл проекта: `.claude/skills/cross-review/SKILL.md`
→ вызывается как `/cross-review` в любой сессии этого проекта.

Альтернатива (не выбрана по умолчанию): секция в CLAUDE.md — правило было бы
всегда в контексте, но зря тратит токены, когда ревью не нужно.

## Драфт правила (содержимое SKILL.md)

```markdown
---
name: cross-review
description: Кросс-ревью или обычное ревью изменений по универсальному чек-листу.
              Два участника (Ревьюер A / Ревьюер B), раунды, спорные пункты,
              голосование. Для небольших диффов — одиночный проход.
---

# Ревью изменений

## 1. Контекст (что ревьюим)

Область ревью определяется так (по убыванию приоритета):

1. Явно указано пользователем: diff, коммит, PR, файлы, директория.
2. В текущем диалоге велась разработка → изменения этого диалога
   (git diff working tree, затронутые файлы, включая новые).
3. Ничего не изменено и не указано → последний коммит.

Перед стартом — одна строка: какая область ревьюится и её размер
(число файлов / строк диффа). Если область неоднозначна — спросить.

Контекст проекта собирается автоматически: стек (iOS/backend/admin),
паттерны соседних фич, конвенции из CLAUDE.md и docs/. Конкретные имена
файлов фичи в правиле НЕ фиксируются — универсальность.

## 2. Выбор режима

- **Обычное ревью** (одиночный проход): дифф < ~150 строк, или пользователь
  попросил быстро, или изменения малорисковые (документы, конфиги, контент).
- **Кросс-ревью** (полный протокол): дифф ≥ ~150 строк, затронуты
  безопасность/миграции/контракты API, или пользователь попросил явно.

В обычном ревью — один проход по чек-листу (раздел 4), тот же формат
таблицы (раздел 5), без раундов и защитника.

## 3. Правила процесса (кросс-ревью)

1. Два участника: Ревьюер A и Ревьюер B. Ходы строго по очереди.
   Участники — отдельные агенты (разные модели/контексты); оркестрацию
   раундов ведёт основная сессия. Ревьюер не видит рассуждений второго —
   только его таблицу замечаний и вердикты.
2. Ход Ревьюера: разбор диффа/файлов по чек-листу (раздел 4). Каждое
   замечание — с файлом, строкой, категорией (bug / security / data /
   network / architecture / tests / UX / style) и severity
   (blocker / major / minor / nit).
3. Ход Защитника (второй участник): по каждому замечанию —
   «согласен, fix» / «не согласен, потому что…» (с обоснованием кодом).
   Спорные фиксируются как disputed.
4. Смена ролей: тот, кто защищал, следующим раундом выступает ревьюером
   и разбирает ТОЛЬКО disputed-пункты и новую область, которую ещё
   никто не смотрел.
5. Максимум 3 раунда. Раунд 3 — «голосование»: каждый участник даёт
   вердикт по каждому disputed-пункту: BLOCKER / ACCEPT / ACCEPT-WITH-NOTE.
   Если за 3 раунда не сошлись — оба варианта и цена каждого решения
   выносятся пользователю.
6. Запрещено: соглашаться «из вежливости», дублировать уже признанные
   замечания, гипотетические проблемы без пути к файлу и строки,
   менять код до финального согласования (ревью сначала, правки после).

## 4. Чек-лист ревьюера (универсальный)

- **Correctness**: логика и граничные случаи; состояния UI/потоки — все ли
  переходы достижимы и обработаны; race conditions (async, повторные
  вызовы, жизненный цикл); валидация входных данных; обработка ошибок.
- **Security**: хранение секретов/токенов; логирование чувствительных
  данных; injection (SQL, команды, XSS); проверка прав на границах
  (API-эндпоинты, пользовательский ввод).
- **Data/DB**: миграции (обратимость, риск потери данных); согласованность
  сущностей и связей; новые запросы — индексы, N+1.
- **API/Network**: согласованность контрактов клиент-сервер; таймауты,
  повторы, коды ошибок; версионирование/обратная совместимость.
- **Architecture**: границы слоёв (Data не протекает в Presentation и т.п.);
  соответствие паттернам соседних фич проекта; дублирование вместо
  переиспользования.
- **Tests**: покрытие нового/изменённого поведения; хрупкие тесты;
  маскировка реального поведения моками.
- **UX** (для UI-изменений): состояния загрузки/ошибок/пустых данных;
  локализация (все языки проекта обновлены); доступность; клавиатура,
  жесты, dismiss.
- **Гигиена**: dead code, TODO, недоделки, debug-логи, закомментированный
  код, неиспользуемые зависимости.

## 5. Формат вывода

| # | Файл:строка | Категория | Severity | Замечание | Статус (accepted/disputed/fixed) |

Итог: список подтверждённых blocker/major с конкретными правками
(diff-предложения); disputed — отдельным блоком для пользователя.
```

## Шаги реализации (после подтверждения)

1. Создать `.claude/skills/cross-review/SKILL.md` с правилом выше.
2. Оркестрация кросс-ревью: основная сессия запускает раунды через агентов
   (Ревьюер A — ecc:code-reviewer; Ревьюер B — вторая модель), собирает
   таблицы, ведёт состояние disputed, проводит голосование.
3. Прогнать правило на живом материале — незакоммиченные изменения
   working tree (backend content + iOS Lesson) — и показать формат вывода.
4. По результатам прогона при необходимости подправить формулировки.

## Что НЕ входит

- Изменение существующих ECC-скиллов (ecc:code-review и др.) — правило
  самостоятельное, ECC используется как источник агента-ревьюера.
- Никаких других файлов проекта план не трогает.
